# credit — 卒業要件チェック

工学院大学・情報学部コンピュータ科学科・2024年度入学生向けの、**大学非公式の卒業要件チェック**です。成績PDFを読み取ると、算入単位、区分別不足、未修得必修、選択必修の条件を決定的なルールで確認します。大学の正式な卒業判定や在学期間の確認は行いません。

## 最初に動かす

Node.js 22.12以上（22系推奨）とnpmを使用します。VS Codeでこのフォルダを開き、ターミナルで実行してください。

```sh
npm.cmd ci
npm.cmd run dev
```

表示された `http://127.0.0.1:5173/` を開きます。

1. 「デモを始める」を押す（架空データ専用、実在学生の情報は入れない）。
2. デモが入力した年度・学部学科を確認する。
3. 「架空の成績を読み込む」または「全条件充足のデモ」を押す。確認画面を挟まずに結果が出る。
4. 「印刷・PDF保存」でブラウザの印刷画面を開く。
5. 読み間違いを直す場合は「成績を修正する」→「結果を更新する」、消去は「リセット」。

デモはVite開発モードかつlocalhost/127.0.0.1のみです。`npm.cmd run build` の成果物では有効化できません。環境変数やURLパラメータによるデモ有効化機能はありません。デモでは実PDFの選択を無効にしています。

## 検証と公開用ビルド

```sh
npm.cmd test
npm.cmd run build
npm.cmd run test:e2e
npm.cmd run test:production
npm.cmd run preview
```

ブラウザテストはWindowsのMicrosoft Edgeを使います。別環境では `playwright.config.ts` の `channel` を変更し、必要なPlaywrightブラウザを用意してください。テストは架空データのみです。

`dist/` が静的配信する成果物です。GitHub Pagesにも配置できます。公開用ビルドも認証なしで利用できます。公開やGitHubへのプッシュはこの実装作業では行っていません。

## 技術と設計

既存はREADMEだけだったため、React + TypeScript + Viteを採用しました。段階的な入力画面を管理しやすく、型検査が可能で、GitHub Pages向けに静的ビルドできます。PDF.jsはローカルにバンドルし、CDNへ成績を送らずブラウザ内で文字を取り出します。Zodでルールデータを実行時にも検査します。生成AIは判定にもPDF抽出にも使用しません。

```text
src/
  auth/session.ts         Googleログイン・署名検証
  data/registry.ts        大学/学科・学籍番号・カリキュラム選択
  data/kogakuin-2024.json 科目、年度別の扱い、根拠、判定ルール
  data/course-master.json 科目マスター（情報学部4学科の科目名・単位数・群）。生成物
  data/demo.ts            開発モード専用の架空成績
  domain/schema.ts        共通データ型・Zodスキーマ・整数単位演算
  domain/validate.ts      ルール参照・上限配分・版の整合性検査
  domain/engine.ts        科目照合・重複排除・上限・条件判定
  domain/master.ts        科目マスターの検査・照合（自学科／他学科・類似科目）
  domain/summary.ts       単位の集計（取得・落単・履修中・評価ごと）
  pdf/normalize.ts        PDF文字行→共通成績形式
  pdf/read.ts             PDF.jsによる端末内の文字抽出
  ui/                    日本語の画面・印刷用CSS
scripts/build-course-master.mjs  公式カリキュラム表PDFから科目マスターを生成
tests/                   単体・ブラウザテスト（別年度の架空条件含む）
docs/evidence.md         公式資料との対応と未確定事項
```

科目そのものと、カリキュラム別の単位・区分・必修種別は `courses` と `placements` で分離しています。公式科目コードは資料にないため `null` です。内部IDを公式コードとして扱いません。科目名が一致しても複数候補なら自動照合しません。学科の異なる「機械学習」などは別科目として扱う必要があります。

## 利用フロー（学内Googleログイン）

`VITE_GOOGLE_CLIENT_ID` を設定すると、最初に学内Google（`@g.kogakuin.jp`）ログインを必須にできます。設定方法は `.env.example` を参照し、`.env.local` を作成してください。クライアントID未設定（開発時の既定）では、ログインを省略して手入力で進めます。デモも開発モード限定で従来どおり使えます。

1. ログインが有効な場合：非公式ツールであることへの同意にチェックし、`@g.kogakuin.jp` でログインします。メールアドレスの学籍番号から入学年度・学部・学科を自動判定します。
2. ログインが無効な場合：最初の画面で入学年度「2024」、学部「情報学部」、学科「コンピュータ科学科」を入力します。学籍番号は任意で、入力時のみPDF内の番号と照合します。
3. 適用条件を確認してチェックし、「成績の取り込みへ」を押します。
4. PDFを選択するかドラッグ＆ドロップします。読み取り後、すぐに結果が出ます。読み取れなかった行や読み間違いは、結果画面の「成績を修正する」から直します（修正画面は最初、要確認の行だけを表示します）。
5. PDFが読めない場合も手入力に進めます。実Ku-port PDF書式は未検証です。

成績とPDFは端末内のメモリだけで処理し、外部サーバー・外部AIへは送信しません。所属はログインで学内アカウントの保有までは確認しますが、学籍番号から導いた適用カリキュラムが卒業判定上正しいことは保証せず、本人対応未確認のままとします。別年度・別学科は未対応として止めます。
ログインを使う場合のみ、認証時に `accounts.google.com`（GSIスクリプトの読み込みと公開鍵での署名検証）と通信します。成績そのものはこの通信に含めません。クライアント登録・ドメイン制限（`VITE_ALLOWED_EMAIL_DOMAINS`）・署名・期限・nonce・`hd` 検証は `src/auth/session.ts` が担い、`App.tsx` から接続済みです。

## 学籍番号と適用範囲

依頼者提供の `J124241` → J=情報学部、1=コンピュータ科学科、24=2024年度を対応表にしています。NFKC、前後空白除去、大文字化を行います。初期版の入力は例に合わせ「英字1文字+数字6桁」に限定していますが、**大学公式の桁数仕様ではありません**。別形式は要確認、他年度・他学科は未対応とし、近いカリキュラムに自動変更しません。

所属・入学年は候補に過ぎません。適用カリキュラムを本人に確認してもらいます。編入、転学科、特例は本対応ではなく、教務窓口で確認が必要です。学籍番号とPDFの番号が不一致・複数なら判定を停止し、入力修正または再取り込みを促します。PDFに番号がない場合は本人確認未完了と明示します。

## PDF抽出の対応範囲と未検証事項

実際のKu-port成績一覧表（文字PDF）の列を座標から読み取ります。**1件の実サンプルで検証済み**ですが、全書式を網羅した完成版ではありません。

- 文字情報のあるPDFを20MB・100ページ・3000文字行まで受け付ける。
- 文字の座標から行候補を作り、原文とページを保持する。
- 「成績一覧表」ページの列（科目／単位数／評価／年度／学期／教員氏名）を、見出し行から学習した列位置で分離する。空欄（Fの単位数欄など）があっても列をずらさない。
- 「年度学期GPA推移表」「年度GPA推移表」「単位修得状況表」のページは明細として取り込まない（集計の合計には履修中単位が含まれるため卒業要件には使わない）。
- 科目名先頭の「※」は現在履修中として扱い、修得に算入しない（原本の注記どおり）。
- 評価から修得状況を決める（公式 `gpa_2024.pdf`：A+/A/B/C/D は合格、Fのみ不合格）。1行ずつの本人確認は求めず、読み取った内容で判定する。
- 折り返した教員氏名の断片を新しい科目として扱わない。
- 次の明示的な区切り形式も列として読む（検証用の交換形式で、Ku-portの仕様ではない。テスト用）。

```text
科目名 | 科目コード | 単位数 | 評価 | 修得年度 | 修得状況
Basic English I | | 1 | 任意の原記号 | 2025 | 修得
```

- 科目名の照合は完全一致/NFKC・空白正規化/明示した別名だけを使用する（略称の例：`Basic Eng.I`→`Basic English I`）。類似度による自動統合はしない。
- PDFでは空欄になるFの単位数を、科目マスターから補う（画面に「マスターで補完」と表示）。マスターにない科目は本人に単位数の入力を求める。
- 「情報系他学科科目」の見出しの下にある科目は他学科の科目として扱う（後述）。卒業判定には自動算入せず要確認のまま残す。
- 修正画面で評価記号を変えると、修得状況は要確認に戻す。
- 成績外の行を本人が除外でき、原文とともに復元できる。
- 画像のみ・文字なし、破損、暗号化、サイズ超過は理由と再出力/手入力の案内を表示する。OCRは未実装。

今後、他の学科・年度やレイアウト差のある実PDFを入手した際は、匿名化サンプルで列座標・改ページ・複数行科目・認定・再履修・学籍番号を再確認します。判定エンジンはPDF書式に依存させません（読み取りは `pdf/` に限定）。

## 科目マスターと単位の集計

`src/data/course-master.json` は、情報学部4学科の2024年度入学生用カリキュラム表（学則別表第１、各PDFの2・3ページ）から生成した科目マスターです。科目ごとに正式名・別名・単位数・開講学科・群（第Ⅰ群／第Ⅱ群a・b／第Ⅲ群／その他）を持ちます。コンピュータ科学科の分は判定データ（`kogakuin-2024.json`）と同じ科目IDで、名前・単位数の一致をテストで保証しています。

```sh
# 公式PDF 4件（2025info1.pdf / 2025info2.pdf / 2025info3.pdf / 2025info4re1.pdf）を任意のフォルダに保存してから
node scripts/build-course-master.mjs <PDFのフォルダ>          # JSONを生成
node scripts/build-course-master.mjs <PDFのフォルダ> --check  # 抽出結果を表示するだけ
```

PDFはGitに入れません。ハッシュ値が記録と違う（改訂された）PDFは拒否します。群・区分は表の罫線から判定します。マスターのJSONは手で編集しないでください。

**学科の扱い**：成績PDFには科目ごとの開講学科が出ません。そこで次のように扱います。

- 基本は自学科の科目とみなす。
- 「情報系他学科科目」の見出しの下にある科目だけ、他の3学科の第Ⅱ群b・第Ⅲ群から探す（学部枠の対象はこの2つだけ。p4注1）。
- 自学科と同名の他学科科目（例：「機械学習」はCS第Ⅲ群Aと情報科学科の両方にある）は、見出しで区別し、名前だけで同じ科目にしない。
- 他学科の科目は、学部枠（最大6単位・選択扱い）として卒業判定に自動で算入する。専門71単位と合計124単位に入り、必修・選択必修の条件には入らない。
- p4注1の類似科目13件（`excludedExternal`）に当たる他学科科目は算入せず、「学部枠に算入できない」と表示する。
- 同名の科目が複数の他学科にあり、単位数か算入可否が違う場合だけ、本人に開講学科を選んでもらう。扱いが同じなら候補をすべて表示する（例：デジタル信号処理は情報通信工学科と情報デザイン学科にある）。

**単位の集計**（結果画面）は、公式 `gpa_2024.pdf` の考え方に合わせています。

- 同じ科目は最も良い評価の1回分だけ数える。そのため、Fのあと再履修で合格した科目は落単に含めない。
- 落単＝最も良い評価がFのままの科目。再履修中（※）の場合は「再履修中」と添える。
- 履修中の単位は、Ku-portの単位修得状況表と同じく、落単科目の再履修分も含む。
- 評価ごとの単位（A+〜F）を表示する。GPA・GPTは表示しない。
- 要確認の行も含めた成績一覧そのものの集計で、卒業判定の算入単位とは別。

## 判定の方針

- 単位は小数第2位までを100倍した整数で計算し、浮動小数点の加算誤差を避ける。
- 修得済みの既知科目（自学科の科目と、識別できた他学科の科目）だけを算入する。不合格・履修中・未評価は別扱い。
- 同じ内部科目ID（または根拠付き代替先）を一回だけ数える。原データの順序に依存しない。
- 要確認にするのは、修得状況が決まらない行、マスターにない科目、単位数がマスターと違う行だけ。推測補正しない。
- 他学科枠は最大6単位。
- 要確認の行がある場合は全体を「要確認」にする。算入単位は下限値。条件ごとに充足・未充足・要確認を表示。
- 区分の不足単位は重複するため合算しない。合計124単位の条件は独立に計算する。
- 全条件が充足しても「確認できた単位要件を充足」と表示し、卒業可と断定しない。

## 新しい年度・学科を追加する

1. 対象入学年度の公式カリキュラム・条件表・注記を取得し、本文の対象年度を確認する。公開年度と入学年度を区別する。
2. 表の結合セルを画像で確認し、科目・区分・必修・選択必修・例外をレビューする。
3. `src/data/` に新しい不変ID/版のJSONを作る。元データを上書きせず、根拠URL・ページ・確認日・確認状態・ハッシュを残す。
4. 科目ID・公式コード（ある場合のみ）、正式名、確認済み別名、開講学科を追加し、`placements` にカリキュラム固有の扱いを書く。
5. `rules` に合計、区分、全必修、選択集合条件を追加する。`assessment` は卒業/進級/卒論着手を区別する。画面は現在、卒業だけを表示する。
6. 代替・同等科目は出典付き `equivalences` に定義する。複数段の代替や曖昧な対応は拒否する。
7. `releaseStatus` を `preparing` で作成し、テスト・根拠レビュー完了後だけ `verified` にする。架空テストは `fixture` とし、通常のレジストリへ登録しない。
8. `registry.ts` に検証済みデータと所属・入学年度の対応表を追加する。未対応の範囲を自動補完しない。
9. 全充足、必修不足、区分不足、選択集合不足、重複、小数、上限、除外、未知科目、別年度混入を検証する。同名科目の単位・必修種別が違うケースも追加する。

対応するルール式は `credits`（選択集合の最低単位）、`count`（最低科目数）、`allCourses`、`and`、`or`。集合は区分・必修種別・科目ID・他学科フラグで指定します。科目は一つの区分にのみ所属し、親条件（合計・専門全体）では同じ科目を参照できますが、合計に二重算入しません。

重なる上限、上限単位を複数区分に配分する部分集合、未知のルール形式はエラーにして停止します。配分最適化や同時所属のルールはまだ対応していません。対応済み形式ならデータの追加だけで共通エンジンを変更せずに拡張できます（別年度・別学科の架空データでテスト）。

## 個人情報

成績PDF・氏名・学籍番号・成績は外部サーバー、外部AI、解析サービスへ送信しません。データはReactのメモリ上にのみ保持し、再読み込み/終了で消えます。印刷したPDFは利用者が自分で管理してください。実在学生のPDFや認証情報をGitに追加しないでください。`.env`、PDF、ログ、テスト出力は除外しています。

Google認証の通信や、静的サイト配信自体に伴うホスティング事業者のアクセス記録は別です。本番ホスティング側にも、URL・成績を含むログやアクセス解析を追加しない運用が必要です。

PDF.jsの日本語CMap・標準フォント・WASMは、起動・ビルド前に依存パッケージから public/pdfjs/ へコピーします。配信元はアプリと同一で、外部CDNを使いません。

## チームへの共有（GitHub Pages）

`.github/workflows/pages.yml` はmainへのpush時にテスト・ビルドし、distだけをGitHub Pagesに配信します。認証なしの公開サイトになります。PDFや成績はブラウザ内で処理します。

1. リポジトリの Settings → Pages → Build and deployment → Source で GitHub Actions を選択します。設定権限がなければ所有者に依頼してください。
2. この設定ファイルの変更をmainへマージします。
3. Actions → Publish GitHub Pages が成功するまで待ちます。main反映後にPagesを設定した場合は、Run workflowでmainを選んで実行できます。
4. 公開完了後のURLは https://ryou2005.github.io/credit/ です。GitHub Pagesの画面・実行結果に表示されたURLでも確認してください。

以降はmain更新で再公開されます。ソースのブランチをそのまま配信する設定は使いません。サイト公開と正式な卒業判定・実PDFの検証完了は別です。
